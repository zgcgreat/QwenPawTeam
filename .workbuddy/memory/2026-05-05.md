# 2026-05-05 Working Memory

## 新增运营统计模块 (ops_analytics)

完成了用户使用情况运营统计功能的开发，包含以下文件:

1. **src/qwenpaw/ops_analytics/models.py** - Pydantic 模型定义
   - DashboardOverview: 仪表盘概览（总用户数、总会话、总消息、每日活跃趋势、渠道分布）
   - UserDetail: 单个用户的详细统计（消息数、会话数、活跃天数、每日趋势、工具使用）
   - DailyActivity: 每日活动统计（DAU、消息数、会话数）
   - ChannelBreakdown: 渠道维度统计
   - TokenUsageSummary: Token 用量汇总
   - UserBrief: 用户简要信息

2. **src/qwenpaw/ops_analytics/service.py** - 服务层实现
   - OpsAnalyticsService.get_dashboard(): 从 workspace/sessions, chats.json, token_usage.json 聚合计算仪表盘数据
   - OpsAnalyticsService.get_user_detail(): 按用户 ID 统计详细信息（消息趋势、渠道分布、工具使用）

3. **src/qwenpaw/app/routers/ops_analytics.py** - API 路由
   - GET /api/ops-analytics/dashboard - 获取仪表盘概览数据
   - GET /api/ops-analytics/users - 获取用户活跃列表（按日统计）
   - GET /api/ops-analytics/users/{user_id}/detail - 获取单个用户详细统计

4. **src/qwenpaw/ops_analytics/__init__.py** - 模块导出
5. **src/qwenpaw/app/routers/__init__.py** - 注册了 ops_analytics 路由

数据源:
- workspace/sessions/*.json (会话消息)
- workspace/chats.json (元数据: user_id, channel, created_at)
- workspace/token_usage.json (Token 用量)

统计维度:
- 日/周/月活跃用户 (DAU/WAU/MAU)
- 渠道分布统计
- Token 用量按模型/Provider 细分
- 工具调用次数排行
- 单个用户的消息趋势和会话列表

## 新增资源用量分析页面 (Resource Analytics) - 2026-05-17

完成了一个全新的资源用量分析功能，展示各 Agent/Model/Provider 的 Token 消耗和调用次数统计：

**后端（Python/FastAPI）**：
- `src/qwenpaw/app/routers/ops_analytics.py` — 新增 `/resource-summary` 端点，复用 service.get_resource_summary()

**前端（React/TypeScript）**：
- `console/src/api/types/resourceSummary.ts` — TypeScript 类型定义 (ResourceMetricItem, DailyTrendItem, ResourceSummaryResponse)
- `console/src/api/modules/resourceSummary.ts` — API 客户端方法 (getResourceSummary)
- `console/src/api/index.ts` — 注册 resourceSummaryApi 到全局 api 对象
- `console/src/pages/ResourceAnalytics/index.tsx` — React 页面组件（使用 @ant-design/plots Column/Pie 图表）
- `console/src/pages/ResourceAnalytics/index.module.less` — CSS Modules 样式文件
- `console/src/layouts/MainLayout/index.tsx` — 路由注册 + lazyImport ResourceAnalyticsPage
- `console/src/layouts/Sidebar.tsx` — 侧边栏导航菜单项（settings-group）+ collapsed nav items
- `console/src/layouts/constants.ts` — KEY_TO_PATH 映射 (resource-analytics -> /resource-analytics)
- `console/src/locales/zh.json` + `en.json` — i18n 翻译资源

**功能特性**：
- 日期范围选择器（默认最近 7 天）
- Agent 筛选下拉菜单（从 API by_agent 数据动态生成选项）
- 4 个统计卡片（Prompt Tokens / Completion Tokens / 总调用次数 / 总 Token 数）
- Token 消耗趋势柱状图（Prompt vs Completion，按日期分组）
- 调用次数趋势柱状图（按日期聚合）
- 智能体/模型/提供商分布饼图（各取 Top 10，带 Spider 标签）

**数据流**：
前端 API → GET /ops-analytics/resource-summary → service.get_resource_summary() → 返回 ResourceSummaryResponse

ResourceSummaryResponse 结构：
- totals: ResourceMetricItem (name="TOTAL") — 汇总统计
- by_agent: ResourceMetricItem[] — 按智能体分组的 Token/调用统计
- by_model: ResourceMetricItem[] — 按模型分组的 Token/调用统计
- by_provider: ResourceMetricItem[] — 按提供商分组的 Token/调用统计
- daily_trend: DailyTrendItem[] — 每日 Token/调用趋势数据

**服务层关键逻辑**（service.py）：
- 从 token_usage.json 读取全局 Token 用量数据
- 扫描 sessions/ 目录，用 stem.split("--", 1) 提取 user_id
- 按比例分配算法估算每个用户的 Token 消耗：user_ratio = user_msg_count / total_all_msgs

## SuperCorp Skill 问题诊断 - 2026-05-17

对 SuperCorp skill（14角色体系、8阶段管线）进行了完整的问题分析，识别出以下关键问题：

### 高优先级 (🔴)
1. **Agent上下文加载爆炸**: Phase加载多个agent prompt（如Phase 2需加载architect+researcher），context window快速耗尽
2. **清窗策略不够彻底**: "清除详细对话历史"依赖手动实现，无自动机制检测/压缩超过阈值的对话轮次
3. **阶段切换过度串行**: 8个Phase顺序执行，无并行化或跳过逻辑

### 中优先级 (🟡)
4. **Hook系统未落地**: hooks/README.md存在但Stage/UserPromptSubmit/Statusline Hooks依赖外部hook管理器实现
5. **Party Mode触发条件模糊**: "重大分歧""争议激烈"是主观判断，无量化指标
6. **7级压缩策略缺乏自动切换机制**: 定义在规则文件中但没有Token Manager自动升级的实际逻辑

### 低优先级 (🟢)
7. **14个Agent角色过多**: 大部分场景只用到3-5个，冗余prompt增加Token消耗
8. **模板目录(cTemplates/)与skills/职责重叠**: templates/*.md（20+文件）与skill文件内容部分重复
9. **状态文件格式不统一**: state.md、progress.md、decisions.md等格式各异，无schema校验
